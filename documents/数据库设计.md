> ==sha256的作用==
>
> - 上传相同文件时，可以通过sha256检查是否已存在，避免重复存储，节省存储空间
> - 可以用于**构建唯一文件标识**，如`/files/{sha256}.{ext}`，避免文件名冲突
>
> ==mime_type字段==
>
> * 安全防护
>
>   - "在文件上传场景中，服务器可以通过校验MIME类型限制用户上传的文件类型，防止恶意文件（如可执行文件）被上传。"
>   - 示例（Python）：`allowed_mime = {'image/jpeg', 'image/png'} if uploaded_file.mimetype not in allowed_mime: raise ValueError("仅支持JPEG或PNG图片！")`
>
> * 正确文件处理
>
>   - 知识库[6]提到："浏览器根据Content-Type响应头中的MIME类型决定如何处理文件"
>   - 例如：`image/jpeg`会显示为图片，`application/pdf`会触发PDF下载
>
> * 文件类型验证
>
>   - 上传文件时，系统可以验证文件的实际类型是否与上传的扩展名一致
>   - 防止用户上传"恶意文件"（如将.exe文件命名为.jpg）
>
> * 用户体验
>
>   - 系统可以正确识别文件类型，提供相应的预览功能
>   - 例如：图片文件可以显示缩略图，PDF文件可以提供预览功能
>
>   **示例**：如果用户上传了一个文件，名为`document.jpg`，但实际内容是PDF，系统可以通过`mime_type`字段检测到这不是图片，而是PDF，从而拒绝上传或提示用户。

#### kb_chunk

`kb_chunk` 分片表：存储解析后的文本分片及向量嵌入，用于 RAG 检索。

> 向量维度 1024（text-embedding-v3），使用 pgvector 存储和检索。

| 字段名      | 数据类型      | 说明           | 备注 |
| ----------- | ------------- | -------------- | ---- |
| id          | bigserial     | 主键           | [非空]自增 |
| library_id  | bigserial     | 所属知识库     | [非空]外键 → `kb_library.id` |
| media_id    | bigserial     | 关联媒体文件   | [非空]外键 → `kb_media.id` |
| content     | text          | 原始文本内容   | [非空] |
| embedding   | vector(1024)  | 向量嵌入       | DashScope text-embedding-v3 生成 |
| chunk_index | int4          | 分片序号       | [非空]同一media内的顺序号 |
| metadata    | jsonb         | 扩展元信息     | 可存储：页码、来源文件、章节标题等 |
| created_at  | timestamp(0)  | 创建时间       | [非空]默认 now() |

> **索引建议**：
> - `(library_id)` — 按知识库检索
> - `(media_id)` — 按媒体文件检索
> - `USING hnsw (embedding vector_cosine_ops)` — HNSW 向量索引，加速相似度查询
>
> **相似度查询示例**：
> ```sql
> SELECT id, content, 1 - (embedding <=> $query_embedding) AS similarity
> FROM kb_chunk
> WHERE library_id = $library_id
> ORDER BY embedding <=> $query_embedding
> LIMIT 10;
> ```
>
> 需要在 PostgreSQL 中启用 pgvector 扩展：`CREATE EXTENSION IF NOT EXISTS vector;`



> **media_id 外键什么作用？**
>
> | 场景           | 为什么需要 media_id                                          |
> | -------------- | ------------------------------------------------------------ |
> | **溯源**       | 回答时标注"内容来自 xxx.pdf 第5页"，用户可跳转原文           |
> | **增量更新**   | `DELETE FROM kb_chunk WHERE media_id = ?` — 只删这一个文件的块 |
> | (**幂等保护**) | `media_id + chunk_index` 可建唯一约束，防止重复插入          |
>
> (**检索只关心"哪个知识库"**，`media_id` 对检索算法没有直接作用)

> #### 为什么需要`chunk_index`字段
>
> `chunk_index` 是**文档内分块的顺序号**，它的作用不在检索层面，而在**文档结构维护**层面：
>
> ##### 核心作用
>
> ##### 1. 保持原文阅读顺序
>
> 一个 50 页的 PDF 被切成 100 个 chunk，召回时需要按原始顺序组织，而不是按相似度排序：
>
> 
>
> ```
> 文档顺序：   chunk_0 → chunk_1 → chunk_2 → ... → chunk_99
>                 ↓
> RAG Prompt 引用时：按 chunk_index 排序拼接，保持上下文连贯性
> ```
>
> 否则 LLM 看到的是语义相似但逻辑跳跃的内容（如先讲"结论"再讲"背景"）。
>
> ##### 2. 支持确定性引用
>
> 在回答中标注来源时，需要精确到"第几块"：
>
> ```
> 回答：Spring Boot 的自动配置原理是...
> 来源：[技术文档-第3页] chunk_index=42
>      [技术文档-第5页] chunk_index=56
> ```
>
> 用户点击引用能跳转到原文位置。
>
> ##### 3. 支持增量更新（幂等保护）
>
> 重新解析同一文件时：
>
> ```sql
> -- 先删旧块
> DELETE FROM kb_chunk WHERE media_id = ? AND chunk_index >= 0;
> 
> -- 再插新块（chunk_index 保持连续）
> INSERT INTO kb_chunk (media_id, chunk_index, content, ...) VALUES (?, 0, ...);
> INSERT INTO kb_chunk (media_id, chunk_index, content, ...) VALUES (?, 1, ...);
> ```
>
> `chunk_index` + `media_id` 可以构成**唯一约束**，防止重复插入。
>
> ------
>
> ##### 但它不参与检索
>
> ```sql
> -- 向量检索只看 embedding，不看 chunk_index
> ORDER BY embedding <=> #{queryEmbedding}
> 
> -- BM25 检索也只看 content，不看 chunk_index
> ORDER BY ts_rank(to_tsvector('chinese', content), plainto_tsquery('chinese', ?))
> ```
>
> `chunk_index` 是**序号线**，不是**检索线**。
>
> ------
>
> ##### 如果没有会怎样？
>
> - 无法保持召回内容的原文顺序 → RAG 回答可能逻辑混乱
> - 无法精确标注"内容来自第几块" → 用户无法溯源
> - 增量更新时无法精确匹配旧块 → 必须全量删除再插入
> - 缺少唯一约束 → 重复解析会积累重复 chunk
>
> 所以 `chunk_index` 是**文档结构元数据**，服务于结果的**可读性和可追溯性**，而非检索算法本身。
